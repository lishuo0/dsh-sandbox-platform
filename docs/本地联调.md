# 本地联调

本机同时运行平台（dsh-sandbox-platform）与脑（dsh-sandbox-brain），
两边共用一个本地 SQLite 文件，在不接阿里云、不安装数据库的情况下跑通
登录、工作区、文件、技能、会话、SSE 和模型对话。有 Docker 时每个工作区跑在
独立容器里；没有 Docker 时回退到 mock（仅本机目录 + 子进程，没有隔离）。
要接 PostgreSQL（部署、多副本、共享库）时改两个 `config.yaml` 的 `database.url`
即可，链路不变。

## 目标与边界

本地替代品只解决「能跑通链路」：

- **OSS**：对象存储换成本地目录（平台 `LocalStore`），不模拟 S3/OSS HTTP 接口。
- **e2b**：本机默认换成一个工作区一个 Docker 容器（脑内 `DockerPlatform`）；
  Docker 不可用时回退到本机目录 + 子进程（`MockPlatform`），后者不提供安全隔离。
- **模型**：仍然是真实模型，登录后点左下角账号菜单里的「模型」填接口地址与密钥，
  或直接调 `/settings/model`（一条能直接跑的命令见 [README 的「脚本」](../README.md#脚本)）。

Docker 模式有内核边界（命名空间、非 root、`--cap-drop=ALL`、只读 rootfs、
只挂当前工作区与只读技能前缀），但本地对象目录仍是所有租户共用的一棵宿主树，
所以本地只适合单用户开发，不是多租户信任边界；多人/生产请用 OSS + e2b。
mock 模式没有隔离：子进程以当前系统用户运行，路径检查只是可信代码里的策略，
不能用于安全测试。

## 前置条件

- 两个仓库同级：`.../dsh-sandbox-platform` 与 `.../dsh-sandbox-brain`
- Node.js 24.9+（SQLite 用的是内置 `node:sqlite`）
- 两仓库都已 `npm install`（脑内部会启动 `@deepseek-ai/dsh`）
- Docker 可选但推荐（macOS 可用 `brew install colima docker && colima start`，
  首次需 `docker pull node:22-bookworm-slim`）；没有 Docker 时自动回退 mock。
  Intel Mac 未装 QEMU 时用 `colima start --vm-type vz` 走 Virtualization.framework。
  PostgreSQL 只在测试跑 PostgreSQL 方言时才需要（见「测试」）
- 脑的插件由内核以 `lib/` 形式导入：首次运行前执行
  `cd ../dsh-sandbox-brain && npm run build`（`dev.sh` 在缺少 `lib/` 时自动构建）
- 脑的 `http.host` 必须是具体地址（默认 `127.0.0.1`）；内核拒绝 `0.0.0.0` 通配绑定

## 配置语义

两边 `config.yaml` 按下面的规则选择数据库和本地替代品：

| 配置 | 留空/设置 | 行为 |
| --- | --- | --- |
| 不写 `database`（或 `database: {}`） | — | 本地 SQLite。平台默认 `var/dsh.sqlite`，脑默认 `../dsh-sandbox-platform/var/dsh.sqlite`，是**同一个文件** |
| `database.file` | 如 `var/dsh.sqlite` | SQLite 模式，按本项目根解析；两边必须指向同一个文件 |
| `database.url` | 如 `postgres://dsh:dsh@localhost:5432/dsh` | PostgreSQL 模式 |
| 平台 `aliyun.oss.*` 任一缺失 | 任意留空 | 使用 `LocalStore`，根目录为 `storage.dir`（默认 `var/objects`） |
| 脑 `aliyun.sandbox.apiKey` | 留空 | 本地沙箱：有可用 Docker daemon 时 `SANDBOX_ADAPTER=docker`，否则回退 `mock`；`DSH_LOCAL_STORE` 指向脑 `storage.dir` |
| `SANDBOX_ADAPTER` | `docker` / `mock` | 显式指定本地适配器。显式写 `docker` 但 daemon 不可用会启动失败；留空则自动探测 |
| `DSH_DOCKER_IMAGE` | `node:22-bookworm-slim` | 沙箱镜像，需带 `sh`、coreutils 和 `find` |
| `DSH_DOCKER_NETWORK` | `none` | 容器网络模式；默认不出网，需要联网时设 `bridge` |
| `DSH_DOCKER_USER` | 宿主 `uid:gid` | 容器内用户；宿主是 root 时用它显式指定非 root 用户 |
| 脑 `storage.dir` | `../dsh-sandbox-platform/var/objects` | 与平台对象目录是同一份 |

判断顺序：`database.file` → `database.url` → 默认 SQLite。两个都写时 `file` 优先，
建议只留一个。配置文件里没有 `database` 这一段也能启动，走默认 SQLite。

脑与平台的 `appKey`、`credentialsKey` 必须一致，但两边脚本各自生成自己的值，
不会互相读取，也不打印这两个值。先启动平台，它会把生成的值写进自己的
`config.yaml`；打开这个文件，把 `credentialsKey` 和 `brain.appKey` 两行原样
填到脑的 `config.yaml` 的 `credentialsKey` / `platform.appKey`，再启动脑。
平台启动输出里只有管理员账号和密码。

> 注意：`config.yaml` 是被 git 跟踪的文件，启动后会被填入随机密钥。
> 不要把这些改动提交进仓库（提交前确认 diff，或本地保留原值）。

### 对象目录布局与挂载映射

平台写入的 key 与脑本地沙箱的 guest 路径一一对应：

| 对象目录 | 沙箱内路径 | 说明 |
| --- | --- | --- |
| `desks/<workspaceId>/...` | `/desk/...` | 工作区文件；每块工作区独占沙箱，挂载点固定 |
| `members/<userId>/skills/...` | `/skillbox/own/...` | 私有技能，沙箱内只读 |
| `common/skills/...` | `/skillbox/common/...` | 公共技能，沙箱内只读 |
| `attachments/v1/file-objects/<sha256>` | — | 附件，脑在未配置 OSS 时回退到本地目录 |

技能文件由平台写入对象目录，脑通过只读挂载读取；对只读挂载的
`files.write/remove/makeDir/rename` 会返回 `unauthorized`。

Docker 模式只为当前工作区创建容器：`desks/<workspaceId>` 以读写 bind mount、
技能前缀以只读 bind mount 进入容器，**不会挂载整个 `storage.dir`**。只读同时由
脑侧路径检查和 Docker 的内核只读挂载兜底，子进程直接 `touch` 也会失败。
mock 模式只做路径检查，子进程不受约束。

## 启动与停止

平台和脑是两个仓库、两个启停脚本。默认 SQLite 模式下脚本只拉起进程（平台 3000、
脑 8080），不启动数据库；两边共用的只有 `database.file` 指向的同一个文件，
平台的 `brain.baseUrl` 指向脑的地址。

```sh
# 终端 1：脑仓库
cd dsh-sandbox-brain
./scripts/dev.sh            # 脑 :8080（SQLite，不启动数据库）

# 终端 2：平台仓库
cd dsh-sandbox-platform
./scripts/dev.sh            # 平台 :3000（同一个 SQLite 文件）
./scripts/dev.sh status
./scripts/dev.sh stop

# 用完也把脑停掉
cd dsh-sandbox-brain && ./scripts/dev.sh stop
```

- 平台日志：`var/log/platform.log`；平台 pid：`var/run/platform.pid`
- 脑日志：`dsh-sandbox-brain/var/log/brain.log`；脑 pid 在脑仓库的 `var/run/`
- 对象目录：`dsh-sandbox-platform/var/objects`（脑的本地沙箱映射到同一份）
- SQLite 文件：`dsh-sandbox-platform/var/dsh.sqlite`；删掉它后重启会自动重建 schema

要接 PostgreSQL 时，两个 `config.yaml` 都写 `database.url`；`dev.sh` 按配置里的
`url` 恢复原来的数据库启动逻辑（优先 Docker，其次本机 PostgreSQL）。

端口冲突时 `dev.sh` 会直接报错；先 `lsof -i :3000`（或 8080、5432）确认占用。

## 手动配置模型

模型配置是**每用户**的，key 由平台加密保存，代码与仓库文件里都不落明文。

登录平台后点左下角账号菜单里的「模型」（走 DSH 客户端设置面板），
填接口地址、鉴权密钥、模型列表和默认模型。也可以直接调 API：

```sh
# 1. 登录（账号密码见 dev.sh 输出）
curl -s http://127.0.0.1:3000/dsh-api/platform/v1/auth/login \
  -H 'content-type: application/json' \
  -d '{"username":"admin","password":"<password>"}'

# 2. 用返回的 accessToken 保存模型配置
curl -s -X PUT http://127.0.0.1:3000/dsh-api/platform/v1/settings/model \
  -H 'authorization: Bearer <accessToken>' \
  -H 'content-type: application/json' \
  -d '{
    "baseUrl": "https://<兼容 OpenAI 的地址>/v1",
    "apiKey": "<key>",
    "modelIds": ["deepseek-chat", "deepseek-reasoner"],
    "defaultModel": "deepseek-chat"
  }'

# 3. 查看（不回显 key 明文）
curl -s http://127.0.0.1:3000/dsh-api/platform/v1/settings/model \
  -H 'authorization: Bearer <accessToken>'
```

约束：

- `baseUrl` 公网地址必须是 `https://`；本机（`localhost`、`127.*`、`::1`）
  和内网（`10.*`、`192.168.*`、`172.16-31.*`）可以用 `http://`。
- 首次保存必须带 `apiKey`，缺失返回 `model-api-key-required`；
  再次保存时若已有 key，可以省略 `apiKey`（页面留空即沿用）。
- `defaultModel` 必须在 `modelIds` 内，否则保存返回 `default-model-not-listed`。
- 模型配置在**创建/恢复会话时**下发给脑；改配置后需要重新创建或恢复会话。

## 冒烟脚本

### `scripts/smoke.mjs`（不需要真实模型）

```sh
./scripts/dev.sh
node scripts/smoke.mjs
# smoke-ok workspace=... session=...
```

验证健康检查、登录、工作区、文件写入/读回、磁盘落盘、会话创建。

模型配置策略（不覆盖已有真实配置）：

- 设置 `DSH_MODEL_BASE_URL`、`DSH_MODEL_IDS`（逗号分隔）时按其保存；
  `DSH_MODEL_KEY`、`DSH_MODEL_DEFAULT` 可选。
- 未设置环境变量时先 `GET /settings/model`：已配置就沿用并打印模型名；
  未配置才写入占位配置并显式警告（真实对话不可用）。
- `DSH_OBJECT_DIR` 可覆盖磁盘校验目录（默认 `var/objects`）。

### `scripts/real-model-smoke.mjs`（可选，调用真实模型）

```sh
DSH_REAL_MODEL_SMOKE=1 node scripts/real-model-smoke.mjs
```

流程：登录 → 创建私有技能 `smoke-answer` → 创建时间戳工作区 → 开会话 →
发消息 → 读平台 SSE，直到收到落库的 `assistant` 事件或实时 `assistant` 分片。

- 本地栈未启动、或该用户未配置模型：打印指引并以 0 退出（跳过，不算失败）。
- 超时默认 120 秒，可用 `DSH_REAL_MODEL_TIMEOUT_MS` 调整；超时会提示查看脑仓库的
  `var/log/brain.log`。
- 会尽力检查工作区是否出现 `smoke-answer.txt`；模型没执行技能只提示、不判定失败。
- 全程不读取、打印或写入模型 key。

## 已知限制

- **Docker 模式有内核边界，但没有持久 rootfs**：容器只挂当前工作区和技能前缀；
  默认以宿主 `uid:gid` 运行（宿主是 root 时用 `DSH_DOCKER_USER` 指定非 root）、
  `--cap-drop=ALL`、`no-new-privileges`、只读 rootfs、`/tmp` 与 `/run` 用 tmpfs、
  pids/内存/CPU 有上限、默认 `--network none`。容器内 `/etc`、`/usr` 等来自镜像，
  不随工作区保留。
- **mock 回退没有隔离**：Docker 不可用时子进程以当前用户运行，可访问整台机器；
  路径 jail 只是策略检查，不能用于安全测试。
- **本地对象目录不是租户边界**：所有工作区共用 `storage.dir` 一棵宿主树，按随机
  `ws_*` 前缀划分，没有 per-user 权限；附件本地 fallback 按 digest 全局共享。
  本地只适合单用户开发，多人/生产请用 OSS + e2b。
- **PTY 与 snapshot 不可用**：`capabilities` 中对应项为 `false`；`pause/resume`
  在 Docker 模式可用，mock 模式不支持。
- **mock 不识别绝对 guest 路径**：子进程的工作目录已被映射，但进程内部写死的
  `/desk/<id>`、`/skillbox/...` 不会被虚拟化；技能内容请走文件 provider。
  Docker 模式的进程本来就在容器里，不受此限。
- **输出有上限**：每个进程只保留 `outputBufferBytes`（默认 1 MiB）的尾部输出；
  重新 `connect(pid, from)` 是**有损**的，起点会被抬到仍保留的第一个字节。
- **只读约束**：Docker 模式由脑侧检查和内核只读 bind 双重约束，子进程写只读目录
  也会失败；mock 模式只拦截 `files` 的写操作。
- **销毁**：Docker 模式 `destroy` 删除容器，容器内进程一并消失；mock 模式只杀
  直接子进程，不递归终止子进程再启动的进程。
- **重启脑**：沙箱（容器）标识会重建，但 `var/objects` 里的数据保留。
- **SQLite 只适合本地单机**：一条连接、一个文件，不做跨机器共享；部署、多副本、
  多人共享库请用 PostgreSQL。

## 测试

默认全部跑 SQLite（临时文件，跑完删除），单元测试不需要 PostgreSQL、不需要 Docker：

```sh
# 平台
cd dsh-sandbox-platform && npm run typecheck && npm run test:unit && npm run test:e2e
# 脑
cd dsh-sandbox-brain && npm run typecheck && npm run test:unit && npm run test:e2e
```

脑的单元测试用内存 Docker CLI 覆盖适配器；`test/e2e/docker-sandbox.test.ts` 会探测
`docker info`，daemon 可用时跑真实容器（首次需要能拉取镜像），不可用时整组跳过。
`test/e2e/docker-isolation.test.ts` 在同一条件下验证隔离：两个工作区互不可见、
容器只挂本工作区与只读技能前缀、非 root / capability 清零 / no_new_privs / seccomp、
`--network none`、无宿主 docker socket，以及工具进程读不到宿主目录与宿主文件。

要回归 PostgreSQL 方言，加 `TEST_DB=postgres`。两仓库共用本机 PostgreSQL 16
测试集群（源码级测试，不依赖 Docker）：

```sh
TEST_DB=postgres npm run test:e2e
```

- 测试集群端口 **55432**，用户 `dsh`，trust 认证，数据目录 `<workspace>/.test-pgdata`。
- 找不到 brew 版 PostgreSQL 时，会自动使用 `<workspace>/.test-pg-bin/native/bin`
  下的预编译二进制（来自 npm `@embedded-postgres/darwin-x64`）。
- 覆盖项：`TEST_PG_PORT`、`TEST_PG_USER`、`TEST_PG_DATA`、`TEST_PG_BIN`。

## 排障

| 现象 | 处理 |
| --- | --- |
| 会话 `createState` 不是 `ready` / 平台 502 | 脑没接上：看 `dsh-sandbox-brain/var/log/brain.log`，确认 8080 监听 |
| `model-config-required` 422 | 地址/模型列表/默认模型缺失，或地址不是 https（本机/内网 http 除外）；先到账号菜单「模型」配置 |
| `model-api-key-required` 422 | 首次配置没带密钥 |
| `default-model-not-listed` 422 | `defaultModel` 不在 `modelIds` 里 |
| 模型报鉴权/网络错误 | 检查 baseUrl、key 是否有效；改完重新创建会话 |
| 端口已被占用 | `./scripts/dev.sh status`，先 `stop` 或改 `http.port` |
| 文件没落盘 | 确认平台 `storage.dir` 与脑 `storage.dir` 指向同一目录 |
| `database is locked` | 有另一个进程长时间占着 SQLite（如重复启动的平台）；`./scripts/dev.sh status` 查进程，等 `busy_timeout`（5 秒）或停掉多余进程 |
| 平台和脑数据对不上 | 两个配置的 `database.file` 解析后必须是同一个文件；`./scripts/dev.sh status` 会打印各自的路径 |
| 启动时 appKey/credentialsKey 不一致 | 两边脚本各自生成，不会自动对齐：从平台 `config.yaml` 复制 `credentialsKey` 与 `brain.appKey` 填进脑的 `config.yaml` |
